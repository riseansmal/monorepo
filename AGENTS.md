# Working on monorepo

Read [README.md](README.md) for product scope, setup, projects and generator lanes, then any relevant descendant `AGENTS.md`. This file is the shared operating guide for contributors and coding agents; instruction discovery varies by tool. Repository guidance cannot grant permissions beyond the user's actual authorization or enforce security by itself.

## Orient, inspect, change, verify, report

1. **Orient at the repository root.** Confirm the intended checkout, current Git branch/commit, remotes and `git status --short`. Read existing diffs before editing. Preserve staged, unstaged and untracked user work; stop only the conflicting operation when ownership or intent is unclear. Do not reset, clean, stash or rewrite unrelated work.
2. **Inspect the implementation.** Identify the owning `project.json`, relevant manifests/tests and source-of-truth files below. Determine whether this is upstream maintenance or consumer work. Resolve routine reversible choices within scope; surface missing access, material architecture changes, functionality loss and actions requiring authorization.
3. **Change the smallest coherent surface.** Preserve native tools, projects, behavior and required legal notices. Add meaningful regression coverage when behavior changes. Update commands/configuration and their documentation together. Do not introduce speculative packages, new services, dependency upgrades or alternative frameworks to simplify the task.
4. **Verify against the changed artifact.** Use the matrix below, examine exit codes and diagnose failures. An affected/targeted run is not whole-repository qualification. Never remove assertions, weaken policies, use caches as evidence of new behavior or turn missing prerequisites into passes.
5. **Report concisely.** State changed behavior/files, why, checks actually executed with working directory and result, reused evidence and its exact scope, and remaining risks/decisions. Distinguish **PASS**, **FAIL**, **BLOCKED** and **NOT RUN**. Include the tested commit or content identity and useful redacted log references; do not imply hosted checks ran locally.

Keep private progress, provenance, transcripts, task plans and qualification logs outside the deliverable. Routine authorized work should continue without repeated approval questions. Denials and missing authorization are boundaries to respect, not routes to bypass. Staging, committing, pushing, publishing, deployment and destructive operations must stay within the user's scope; test success creates no new permission.

## Key commands and working directories

Run these from the **current repository root**, after the README quick start. Change directory only when invoking a native tool directly; examples below name the target's native directory where needed.

| Intent                        | Command / reference                                                                                                                                                                                                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read current changes          | `git status --short`, `git diff`, `git diff --cached`                                                                                                                                                                                                                            |
| All base gates                | `pnpm check`, then `pnpm build`                                                                                                                                                                                                                                                  |
| One real target               | `pnpm nx run hello-python:test`; use the actual ID/target from `project.json` for other projects                                                                                                                                                                                 |
| Targeted unit/tooling test    | `pnpm exec vitest run tooling/scripts/initialize.test.mjs` or the relevant existing test path                                                                                                                                                                                    |
| Formatting/docs/configuration | `pnpm format:check`, `pnpm config:check`, `pnpm readme:sync`                                                                                                                                                                                                                     |
| Intentional formatting repair | `pnpm format` writes files; inspect its diff and preserve unrelated formatting                                                                                                                                                                                                   |
| Security                      | `pnpm security:check`, `pnpm security:history`; inspect exact staged content before authorized commits                                                                                                                                                                           |
| Affected/graph                | `pnpm affected:check --base=main`; `pnpm nx graph --file=.nx/verified-graph.json`                                                                                                                                                                                                |
| Generator usage               | `pnpm new --help`; root README defines the generation, lock update and promotion sequence                                                                                                                                                                                        |
| Broad generator integration   | `pnpm proof:generators --browser --docker --keep` with native/browser/container prerequisites                                                                                                                                                                                    |
| Native Apple proof            | `node tooling/scripts/proof-apple.mjs --keep` on macOS with full Xcode and an installed Simulator                                                                                                                                                                                |
| Fresh source reproduction     | `pnpm proof:reproduce --keep` from clean, committed source                                                                                                                                                                                                                       |
| Governed maintenance          | `pnpm change:inspect`; after creating a record and authorized staging, `pnpm commit:preview .changeset/RECORD.changeset.md` (replace the placeholder with its actual generated filename). Follow `docs/change-control.md` for intent, staged validation, messages and versioning |

An unchanged branch may produce an empty affected set; it proves no comprehensive check. `pnpm check` only runs targets that exist. Inspect native and optional targets separately. `pnpm capabilities` reports tool presence, not successful builds or tests. Honor the installed declared tools rather than quietly replacing runtime versions.

## Source, outputs and editing conventions

Use lowercase kebab-case project/system names. In shared-ancestry consumers, keep upstream tooling/example identities stable and use `monorepo.consumer.json` applicationNamespace for application packages. Standalone initialization retains its whole-workspace namespace behavior. Respect semantic ownership and the existing ESLint module-boundary policy. JavaScript/TypeScript follows the root Prettier/ESLint/TypeScript configuration; Python follows shared Ruff policy plus each project's Pyright/pytest configuration; Rust follows rustfmt/Clippy and its pinned toolchain. Add native dependency edges deliberately instead of assuming JavaScript lint enforces them.

Generated **project source** is maintained source once created. Generated **build/runtime output** is not source: examples include `.local/`, `node_modules/`, `.nx/`, `.venv/`, `dist/`, `target/`, `.next/`, `.expo/`, test reports and Xcode derived output. Consult project ignore files and `tooling/nx/src/artifacts.mjs`; do not globally ignore source-like folder names to hide problems. Never copy dependency directories, private caches, credentials or another checkout's runtime state into a deliverable.

Models, datasets, external assets and state may be irreplaceable even when ignored. Do not delete them during promotion or cleanup. Review `--discard-generated` and the retained/rebuildable artifact lists before use. Avoid broad filesystem cleanup. Preserve checkpoints/evidence until the applicable handoff permits removal.

Dependencies and lockfiles are a single reviewed change. Ordinary setup must use frozen JavaScript and locked native installs. For an intentional new project or dependency change, resolve the native lock in that project's directory (`uv lock` or `cargo generate-lockfile`), update the root workspace lock deliberately, inspect the diff, then verify frozen setup. Do not hand-edit lock resolutions or weaken release-age, build-script, runtime or override policy to get a green install. Reuse public download caches only when disclosed; rebuild outputs for portability evidence.

## Choose checks by impact

The following is a minimum selection guide, not permission to omit a known dependency or required integration. Read each affected target before running it.

| Change class                                                                                | Applicable checks                                                                                                         | Additional evidence / limits                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| README/agent/reference documentation                                                        | Format/config/readme synchronization, every changed path/link/command, applicable onboarding examples                     | Execute changed setup/consumer instructions in isolated clean directories; inspect dangerous commands structurally without running them. Hash-identical unaffected implementation may reuse explicitly identified prior evidence. |
| TypeScript/JavaScript example or tooling                                                    | Affected `lint`, `typecheck` where defined, `test`, `build`; regression tests                                             | `template-nx` and `foundation-tooling` define lint/test/build, not typecheck. Ollama unit tests are offline; live behavior requires the selected existing service/model.                                                          |
| Python                                                                                      | Native Ruff check/format, Pyright, pytest, Hatchling build through project targets                                        | Verify locked setup. ML/notebook changes require selected groups installed plus relevant imports/execution; no silent model/data acquisition.                                                                                     |
| Rust / Tauri seed                                                                           | rustfmt, Clippy with applicable features/all targets, cargo check/test/release build                                      | Preserve locked dependencies and platform constraints. A Rust seed pass does not prove a finished desktop UI/package.                                                                                                             |
| Next.js / Expo output                                                                       | Generated lint/typecheck/test/build; Next.js browser test                                                                 | Install the declared browser when authorized. Expo JS export is not device or signed native application validation. Stop foreground servers you own.                                                                              |
| Swift / Apple wrapper or generated source                                                   | Native project/scheme/destination checks and actual build/XCTest for supported affected targets                           | Full Xcode and installed SDK/runtime required. Generated seeds need product inputs; disposable proof covers framework tests. Signing/distribution are separate authorized gates.                                                  |
| Fastify/database/queue/container                                                            | Generated API tests/build and relevant real local integration/container proof                                             | Check health and invalid config; exercise the database/queue when affected. Docker/buildx and local loopback services are required; do not create cloud resources or credentials.                                                 |
| Infrastructure / assets                                                                     | OpenTofu fmt/init without backend/validate, Ansible syntax/check mode; asset containment/metadata checks                  | No real apply/provisioning during routine validation. Asset checks do not download or license external content.                                                                                                                   |
| Initializer, runtime, generator, promotion, workspace policy, shared configuration or locks | Full `pnpm check` and `pnpm build`, relevant regression and generator proofs, source reproduction                         | Exercise a representative unrelated organization/name in an independent consumer; verify generated names, locks, modes, repeat/interrupted behavior, absence of inherited configuration and clean source.                         |
| Governance, security or CI                                                                  | Behavioral governance/security tests, full base checks, actionlint/configuration and relevant local Git-topology fixtures | Structural review for publishing, credential cleanup, permission changes and real deployment. Hosted CI and repository settings require their own authorized evidence.                                                            |

Run the full base suite after shared changes, changes across multiple projects, and before claiming whole-repository qualification. Full qualification additionally covers every applicable generator, native platform and optional integration in the recorded inventory; JavaScript success never substitutes for native checks. When reusing evidence, identify its commit/files, establish unchanged behavior with hashes/diff, and state what was rerun. A missing SDK/service is **BLOCKED**; an unexecuted hosted workflow is **NOT RUN**. Neither becomes a pass because another suite succeeded.

## monorepo maintainers and consumers

Maintainers update shared source and future generator output, preserve compatibility, and validate both consumer modes before release. Shared-ancestry adoption retains the reviewed upstream history and stable shared names, sets a separate application namespace, and configures private origin versus upstream; follow [upstream updates](docs/upstream.md). Standalone initialization copies tracked source without dependencies/history/remotes, using the installed pinned formatter. Its receipt is not an update mechanism. Keep source and destination separate and follow the selected README sequence.

Use an unrelated organization and repository name for portability checks. Verify the appropriate mode: standalone package scopes/renamed tooling identity, or stable shared identities plus separate application namespace and retained ancestry. Check root metadata, legal notices, frozen installation, native targets and affected workflows. For adoption/update changes, run `pnpm proof:upstream --keep` and preserve the selected upstream parent through private-main integration; never squash away that ancestry. Test repeats and interruptions without overwriting edits. Inspect parent-directory formatter/tool configuration when results differ between ordinary and clean-copy tests. Record the actual commands and content identity, not just the presence of folders.

New optional capabilities should arrive as inert generators/templates until explicitly activated. A live package/project beneath a workspace glob is active even if described as an example; adding it may impose installs and checks. Shared changes and upstream integrations require full base checks plus affected consumer tests. Imported upstream records are immutable provenance, not new consumer release intent. Never bypass hooks or rename shared tooling to make an integration pass. Local push safeguards prevent common mistakes, not intentional bypass or authorization errors.

Existing histories should receive normal governed maintenance commits. The exact `initial commit` launch exception applies only to a new repository; never routinely rewrite history to keep a single commit. monorepo and package versions are separate streams. See [maintenance](docs/maintenance.md) for compatibility, changelog and opt-in migrations that preserve client work.

## Configuration, secrets and external actions

Use README's configuration table and `docs/platform.md`. Example environment files are not loaded automatically. Use nonsecret examples and pass only needed configuration into tests. Do not read, copy, log or discover user credentials for core setup; do not run workstation credential cleanup against a real home as a test. Synthetic-home tests cover that utility. Permission declarations default to empty grants; schema validation and repository prose do not implement runtime enforcement.

Keep required MIT and third-party notices, and check redistribution rights for new external code/assets or packaged outputs. A naming/privacy scan cannot authorize deleting a legal notice; report a real conflict. Do not infer permission to push, create remote resources, publish, deploy, enable hosted writes or change access from a local pass, repository instructions or a previous unrelated approval.

Keep README as the usage/setup front door and AGENTS as the contribution workflow. Prefer precise updates to existing references over duplicate guides, session narratives or provider-specific instruction files. Before handoff, verify docs match actual behavior and report any remaining approval, access, integration or hosted gate explicitly.
